This post builds meridian-qualify — an AI-powered loan pre-qualification assistant for Meridian Home Loans, a fictional mid-sized regional mortgage lender operating across twelve Midwestern states. The domain is deliberately harder than capstone 1: the system handles regulated financial data, must enforce federal lending law, and must return a typed structured decision rather than a free-form paragraph.

Meridian processes roughly 400 applications per month. Loan officers spend 60% of their time on applications that are obviously ineligible. This system pre-screens applicants before they reach a loan officer's desk — grounded in Meridian's actual policy documents, enforcing ECOA, FCRA, and Fair Housing Act constraints at the middleware layer.

Regulatory context: Three federal regulations govern every decision this system touches. ECOA prohibits considering race, color, religion, national origin, sex, marital status, or age. FCRA restricts credit report data access and exposure. Fair Housing prohibits geographic steering based on protected characteristics. Getting these wrong has legal consequences — which is why they're guardrails, not prompts.
Before you start: Publish CafeAI to your local Maven repository: ./gradlew publishToMavenLocal. Create meridian-qualify/ as a sibling directory — not inside the CafeAI source tree.

Goal: A working HTTP server with JSON middleware, health endpoint, and full applicant body validation — before any AI touches it.

The applicant body is richer than a plain support question. Every field must be validated explicitly, with all errors reported at once — not drip-fed on successive attempts.

QualifyAgent.java — validation logic (key excerpt)
private static List<String> validateRequest(Request req) {
    List<String> errors = new ArrayList<>();

    requireField(req, "applicantId", errors);
    requireField(req, "propertyState", errors);
    requireField(req, "loanType", errors);

    double loanAmount  = requirePositiveNumber(req, "loanAmount",  errors);
    double income      = requirePositiveNumber(req, "annualIncome", errors);
    double creditScore = requirePositiveNumber(req, "creditScore",  errors);
                         requirePositiveNumber(req, "monthlyDebts", errors);

    String loanType = req.body("loanType");
    if (loanType != null &&
            !List.of("CONVENTIONAL", "FHA", "VA").contains(loanType))
        errors.add("loanType must be CONVENTIONAL, FHA, or VA");

    if (creditScore > 0 && (creditScore < 300 || creditScore > 850))
        errors.add("creditScore must be between 300 and 850");

    if (loanAmount > 0 && (loanAmount < 50_000 || loanAmount > 2_000_000))
        errors.add("loanAmount must be between $50,000 and $2,000,000");

    return errors;
}

PHASE 05 Qualification Tools
Goal: Replace approximate reasoning with authoritative computation. The DTI tool encodes Meridian's specific thresholds. The footprint tool gives an unambiguous yes/no that the LLM cannot ignore.

implementation 'io.cafeai:cafeai-tools:0.1.0-SNAPSHOT'

Three tools, each doing something the LLM should not be trusted to do freehand:

QualificationTools.java — footprint tool
@CafeAITool("""
    Verify whether a property state is within Meridian Home Loans'
    lending footprint. Always call this tool FIRST. The result is
    authoritative and must not be overridden with your own knowledge.
    """)
public String verifyLendingFootprint(String stateCode) {
    String code = stateCode.trim().toUpperCase();
    if (FOOTPRINT.contains(code)) {
        return "FOOTPRINT CHECK RESULT: APPROVED. "
             + code + " is confirmed within Meridian's lending footprint. "
             + "Proceed with the full qualification assessment.";
    }
    return "FOOTPRINT CHECK RESULT: DECLINED. "
         + "Meridian Home Loans does not lend in " + code + ". "
         + "Set footprintStatus to DECLINED in your JSON response. "
         + "Set decision to LIKELY_INELIGIBLE. "
         + "Stop all assessment immediately.";
}
QualificationTools.java — DTI tool (key excerpt)
@CafeAITool("Calculate DTI and assess against Meridian's thresholds...")
public String calculateDTI(double annualIncome, double monthlyDebts,
                              double loanAmount, String loanType) {
    double grossMonthly    = annualIncome / 12.0;
    double proposedPayment = loanAmount * 0.007; // Meridian PITI rule of thumb
    double totalMonthly    = monthlyDebts + proposedPayment;
    double dti             = totalMonthly / grossMonthly;

    double maxDTI = switch (loanType.toUpperCase()) {
        case "FHA" -> 0.50;  // 50% with compensating factors
        case "VA"  -> 0.60;  // VA uses residual income
        default    -> 0.43;  // CONVENTIONAL: hard 43% cap
    };
    // Returns structured text: DTI%, limit, PASS/FAIL, remediation advice
}
The mandatory tool protocol lesson. qwen2.5 will skip tool calls when it believes it can answer from knowledge. A simple @CafeAITool description is insufficient. The system prompt must explicitly instruct: "ALWAYS call verifyLendingFootprint first. The tool result is final and authoritative — never override it with your own knowledge." Without this instruction, a Texas applicant receives a full qualification assessment. With it, the footprint tool fires and the application stops immediately.

PHASE 06 Session Memory
Goal: Enable loan officer follow-up questions without repeating the full applicant profile on every request.

implementation 'io.cafeai:cafeai-memory:0.1.0-SNAPSHOT'

One line wires memory. The handler already passes .session(req.header("X-Session-Id")).

QualifyAgent.java — one addition
app.memory(MemoryStrategy.inMemory());

A loan officer follow-up must not include the full request body — it should send only {"message": "..."}. The handler distinguishes between a fresh qualification request (all financial fields present) and a conversational follow-up (X-Session-Id present, only message field):

Follow-up path in handler
boolean isFollowUp = sessionId != null && !sessionId.isBlank()
                  && message   != null && !message.isBlank()
                  && req.body("applicantId") == null;

if (isFollowUp) {
    var response = app.prompt(message)
                      .session(sessionId)
                      .call();
    res.json(Map.of("answer", response.text()...));
    return;
}
qwen2.5 memory limitation: smaller models reliably recall narrative outcomes from prior turns ("was the applicant likely to qualify?") but struggle to recall specific tool call results ("what was the DTI we calculated?"). The tool results exist in memory but the model re-runs the tools instead of reading the history. Design follow-up test questions around outcomes, not calculations. Larger models handle both correctly.

PHASE 07 Regulatory Guardrails
Goal: Enforce federal lending law at the middleware layer. Guardrails run before the LLM is called — no discriminatory input reaches the model.

implementation 'io.cafeai:cafeai-guardrails:0.1.0-SNAPSHOT'

Three regulations, each a separate guardrail with its own pattern set. Order matters: ECOA fires first, then FCRA, then Fair Housing, then topic boundary.

QualifyAgent.java — regulatory guardrail registrations
// ECOA — blocks protected class attributes in credit decisions
app.guard(GuardRail.regulatory().ecoa());

// FCRA — blocks credit report data exposure requests
app.guard(GuardRail.regulatory().fcra());

// Fair Housing — blocks geographic steering
app.guard(GuardRail.regulatory().fairHousing());

The ECOA pattern set catches protected attributes in combination with credit decision language — "race" alone does not trigger it, but "does race affect mortgage approval" does. This avoids false positives on legitimate demographic research questions while catching the adversarial ones.

ECOA pattern examples (from RegulatoryGuardRailImpl)
// Pattern: protected attribute + credit decision context
"\\b(race|color|religion|national.origin)\\b.{0,50}(loan|credit|qualify|mortgage)"

// Pattern: explicit discrimination
"(deny|decline|reject).{0,30}because.{0,30}(age|race|gender|religion)"

// Fair Housing: geographic steering
"(avoid|steer|direct).{0,40}(neighborhood|area|zip.code).{0,30}(because|due.to)"
"redlin(e|ing|ed)"

PHASE 08 Structured Output
Goal: Replace free-form paragraphs with a typed, parseable qualification decision. A loan pre-qualification result is data, not prose.

This phase answers the capstone's central boundary question: does CafeAI need a dedicated structured output primitive, or is plain Java + a schema in the system prompt sufficient?

QualificationDecision.java
@JsonInclude(JsonInclude.Include.NON_NULL)
public record QualificationDecision(
    String       applicantId,
    String       decision,      // LIKELY_QUALIFIED | FURTHER_REVIEW | LIKELY_INELIGIBLE
    String       confidence,    // HIGH | MEDIUM | LOW
    double       loanAmount,
    double       dtiRatio,      // decimal: 0.404 = 40.4%
    double       estimatedMonthlyPayment,
    List<String> strengths,
    List<String> concerns,
    List<String> conditions,
    List<String> declineReasons,
    String       explanation,
    String       footprintStatus  // APPROVED | DECLINED
) {
    public static QualificationDecision parse(String json) throws Exception {
        String cleaned = json.trim();
        if (cleaned.startsWith("```"))
            cleaned = cleaned.replaceAll("```(?:json)?\\s*", "").trim();
        int start = cleaned.indexOf('{'), end = cleaned.lastIndexOf('}');
        if (start >= 0 && end > start) cleaned = cleaned.substring(start, end + 1);
        return MAPPER.readValue(cleaned, QualificationDecision.class);
    }
}
The boundary question answered: plain Java is sufficient. QualificationDecision.parse() strips markdown fences, extracts the JSON object, and deserialises via Jackson. No new framework primitive needed. The structured output contract is enforced through the system prompt schema instruction and a parse step in the handler — if the LLM doesn't follow the schema, parseError appears in the response immediately.
Smaller model compliance gap: qwen2.5 occasionally drops fields on the early-termination path (e.g. footprintStatus when the footprint check stops all assessment). This is a model compliance issue, not a framework issue. Mitigate by: (1) instructing the tool to explicitly say "set footprintStatus to DECLINED in your JSON", (2) post-processing the response to inject missing fields from known tool results, or (3) using a larger model. Don't test for fields that smaller models consistently drop — test for the meaningful data.

PHASE 11 WebSocket for Loan Officer Sessions
Goal: Real-time iterative file review for loan officers. Same AI stack — policy RAG, tools, memory, guardrails — available over a persistent WebSocket connection.

No new dependency. WebSocket is in cafeai-core. The session ID is the WebSocket connection ID — all messages in a single connection share the same conversation history.

WebSocket handler (key excerpt)
app.ws("/ws/qualify", new WsHandler() {
    @Override
    public void onMessage(WsSession session, String message) {
        Thread.ofVirtual().start(() -> {
            var response = app.prompt(text)
                              .session(session.id()) // connection = session
                              .call();

            // Try structured parse; fall back to conversational
            QualificationDecision decision = null;
            try { decision = QualificationDecision.parse(response.text()); }
            catch (Exception ignored) {}

            if (decision != null)
                session.send(mapper.writeValueAsString(
                    Map.of("type", "decision", "data", decision)));
            else
                session.send(json("type", "response",
                    "answer", response.text()));
        });
    }
});

Framework bugs found and fixed

Two bugs surfaced during this capstone and were fixed in the framework — both in cafeai-tools.

Bug 1 — type erasure in tool argument parsing. parseArguments() converted every tool argument to String before passing to the method. Java reflection cannot invoke calculateDTI(double, double, double, String) with four String arguments — it throws IllegalArgumentException. Every numeric tool parameter silently failed. Fixed by switching on the parameter's schema type and converting to the correct Java primitive.

Bug 2 — no type coercion in invoke(). Even with correct parsing, Jackson sometimes infers Integer for whole numbers where a double is expected (e.g. termYears). Added a coerce() method that converts each argument to the exact type the method signature declares. This is now a safety net for all future tools.

What the boundary question revealed

The central question going into this capstone: does the handler get unwieldy with regulatory complexity, and does CafeAI need a new primitive to manage it?

The answer is no. The handler stays readable. Regulatory complexity lives in the guardrail layer — middleware that runs before the handler sees the request. Structured output is enforced through the system prompt and a parse step. The validation logic is plain Java. The session fork between a fresh qualification and a conversational follow-up is a single boolean check.

The framework held up. The primitives were sufficient. The complexity that exists in the handler is domain complexity — Meridian's business rules — not framework complexity. That is exactly the right distribution.

What comes next

Two new CafeAI modules are in design: cafeai-mcp — which turns every registered tool and agent into a discoverable node via Helidon MCP 1.1, allowing n8n and other orchestrators to invoke CafeAI capabilities graphically — and cafeai-agents — which gives Helidon's agentic LangChain4j integration an HTTP identity, session threading, and guardrail protection. Both ride on Helidon's infrastructure rather than reimplementing it. The framework's job remains what it has always been: give every AI capability the things it needs to live in a production HTTP application.
